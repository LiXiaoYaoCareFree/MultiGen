# Research Arena 实现分析与优化方案

## 一、代码架构与实现细节

### 1.1 整体架构

Research Arena 的核心是一个状态机驱动的三阶段流水线（Pipeline），每个阶段由CLI Agent自主执行，Agent类型可插拔（Claude Code、Codex、Kimi Code）。

```
Stage(IDEATION) → Stage(SELF_REVIEW_IDEA) → Stage(EXPERIMENTS) 
→ Stage(SELF_REVIEW_EXPERIMENT) → Stage(PAPER) → Stage(SELF_REVIEW_PAPER) 
→ Stage(REVIEW) → Stage(ACCEPTED/FAILED)
```

### 1.2 种子体系（数据构建）

仓库定义了**85个研究种子**（`configs/seeds.yaml`），远比论文中报告的13个多。这是论文实验的子集——论文选择了5个CPU+8个GPU代表性种子。

种子结构包含四个字段：`name`（研究领域名称，Agent自主决定具体问题）、`conferences`（目标投稿会议列表）、`platform`（gpu或cpu，决定资源分配）、`domain`（ml/systems/databases/pl/theory/security，选择Agent阅读的指导模板）。

种子覆盖范围远超SciEval-Bench的学科覆盖：GPU种子包含表示学习、生成模型、计算机视觉、NLP、AI for Science（生物学/物理学/化学/神经科学）、可信AI（公平性/安全性/隐私）、基础设施（ML系统/数据集）、图形学等35个种子。CPU种子包含ML理论（优化/学习理论/因果推理）、系统（操作系统/分布式/数据库）、编程语言（程序分析/编译器/类型系统）、理论CS（算法/复杂度/图算法）、安全（软件安全/密码协议）等50个种子。

### 1.3 三阶段流水线

**IDEATION阶段：** Agent接收种子主题和历史反馈，在独立workspace中产出`idea.json`（研究想法描述）、`proposal.md`（研究提案）和`plan.json`（实验计划）。Agent自主决定具体研究问题——例如种子"计算机视觉"可能产生任何CV子方向的研究。Agent会阅读`templates/`下的领域特定指导（ML/系统/数据库等）。

**EXPERIMENTS阶段：** Agent读取`idea.json`和资源约束信息，产出`exp/`目录（实验代码和产出）、`results.json`（结构化实验结果）。Agent可使用代码解释器、文件系统和网络搜索工具。最多3次重试，失败后根据自评审反馈决定是revise还是abandon。

**PAPER阶段：** Agent接收idea、实验结果、venue信息、历史评审反馈和自评审反馈，产出`paper.tex`和编译后的`paper.pdf`。论文使用LaTeX格式，Agent需处理引用（通过搜索工具查找真实论文）、图表（从实验产出中生成）、公式和排版。

### 1.4 自评审（Self-Review）机制

每个核心阶段之后都有一个自评审关卡：Agent对自己的产出进行评分（0-10分）并提供具体反馈。阈值配置：idea≥8分通过、experiment≥6分通过（实验阶段更宽松）、paper≥8分通过。低于4分直接放弃当前想法（abandon）。5-7分进入revision循环——Agent根据自评审反馈修订当前产出。最多2次revision尝试，超过后虽低分也继续前进（避免无限循环）。

### 1.5 双层评审体系

**外部评审（Stanford Agentic Review，paperreview.ai）：** 仅基于论文PDF，使用0-10分ICLR量表。这是自动化评审，论文PDF提交到外部API。

**Agent交叉评审（Peer Review）：** 使用非研究Agent自身的其他Agent类型作为评审者。评审者接收论文PDF和实验产出，被要求使用工具验证引用真实性、检查实验结果一致性。这是一个Code-Aware评审的朴素实现——评审者可以访问实验代码和产出，但没有系统化的编造检测清单。

## 二、当前未解决的关键问题

### 2.1 引用幻觉问题

Research Arena报告中明确发现：Claude Code 36%论文含虚假引用、Kimi Code 72%论文含虚假引用。虽然评审者被要求"使用工具验证引用"，但验证是审稿人主观判断的，没有自动化的引用验证管线。Agent在论文撰写时通过搜索工具找引用，但搜索可能返回不存在的论文，或Agent编造看似合理的引用格式。

**本质原因：** LLM的生成机制天然倾向于"流畅的虚构"——当Agent在撰写论文时需要引用支撑某个观点，如果搜索未返回理想结果，它会编造一个"应该存在"的论文。引用验证是事后补救而非事前预防。

### 2.2 实验逻辑不完整

报告中出现的典型问题包括：论文声称在87个基准上评估但仅实现20个、声称运行了消融实验但代码中无对应逻辑、设置不匹配（论文说用了Adam但代码用的是SGD）、方法描述与实现不符（声称实现了Transformer但实际是标准MLP）。

**本质原因：** Agent在IDEATION阶段提出实验计划，在EXPERIMENTS阶段执行，在PAPER阶段根据"理想的结果"撰写论文——这三个阶段的产物可能不一致。当实验失败或产出不理想时，Agent倾向于"修复论文"而非"修复实验"。

### 2.3 自评审的偏差

自评审的评分可能不可靠——Claude Code的自评审idea阶段改进率100%，但外部评审揭示这些"通过自评审"的想法在严谨性上仍有严重缺陷。Agent倾向于给自己高分（或根据配置阈值给出刚好通过的低分）。

**本质原因：** 同一Agent评审自己产出的根本性冲突——缺乏独立视角。Pipeline中虽然有三阶段自评审，但它们使用的是同一个Agent类型（只是不同调用），没有真正独立的"第二审稿人"。

### 2.4 缺乏系统化编造检测

虽然引入了双层评审，但SAR完全不检查代码，PR的代码检查是评审者的"自由裁量"而非结构化流程。没有逐项核对清单，没有声明-结果一致性自动比对，没有引用真实性自动验证。

**本质原因：** Research Arena的设计重点在"Agent能否做科研"而非"Agent是否在造假"——编造检测是事后的人工分析，不是Pipeline的内建功能。

### 2.5 资源-质量瓶颈

报告中H100扩展实验的核心发现：更强的GPU不带来更好的研究质量。实验代码经常因CUDA错误、内存限制和训练不稳定而失败——不是GPU不够强，而是Agent不会有效利用。

**本质原因：** Agent生成的代码质量参差不齐，缺乏对GPU内存管理和调试的系统性理解。这是"生成代码"和"生成正确的代码"之间的鸿沟。

## 三、迭代式生成流程能否解决这些问题？

Research Arena已经实现了"自己生成→自己评审→根据评审结果继续生产→循环"的迭代流程。我们来分析它对各问题的效果。

### 3.1 对引用幻觉：有限改善

自评审+外部评审的双层反馈**可以**发现部分引用问题（评审者被要求检查引用），但：Agent在修订时可能用其他虚假引用替换被发现的虚假引用（治标不治本）、没有自动化的引用验证反馈给Agent（评审者说"引用X有问题"，Agent说"那我换引用Y"——但Y也可能是假的）。迭代循环可以降低单次运行的引用错误率，但无法消除系统性编造。

### 3.2 对实验逻辑不完整：部分改善

自评审关卡如果在experiment阶段发现了问题（如"缺少消融实验"），Agent会被送回重新执行实验——这**可以**改善实验完整性。但：自评审可能无法发现所有逻辑漏洞（尤其是需要领域专业知识的）、修订循环有时间限制（最多3次）、Agent可能选择修改论文描述而非修改实验（更容易的路径）。

### 3.3 对自评审偏差：无改善

迭代循环使用的评审者与研究者是同一Agent类型——偏差在循环中会被放大而非纠正。需要引入独立的、不同架构的评审Agent来打破这种自确认偏差。

### 3.4 对编造检测：无改善

当前Pipeline中编造检测不在迭代循环内——它是事后的人工分析。除非将结构化编造检测（逐项核对清单）集成到自评审或外部评审的输出中，否则迭代循环无法解决编造问题。

## 四、基于SciEval-Bench的优化方案

### 4.1 集成自动化引用验证到Pipeline

**方案：** 在PAPER阶段和REVIEW阶段之间插入一个自动化`citation_verify`步骤。提取论文中所有`\cite{}`标记，通过CrossRef API和Semantic Scholar API批量验证每条引用（存在性+标题匹配+作者年份匹配），将验证结果（通过/失败/可疑）注入到评审反馈中。

**代码位置：** 在`pipeline.py`的`_run_paper()`之后、`_run_review()`之前调用。或作为review阶段的前置步骤（`review.py`的`review_paper`函数内）。

### 4.2 引入结构化编造检测清单

**方案：** 借鉴SciEval-Bench的编造检测清单设计。在EXPERIMENTS阶段完成后、PAPER阶段开始前，自动生成一份可验证声明清单：从idea.json提取预期实验设置、从results.json提取实际数值结果、从plan.json提取预期消融实验列表。PAPER阶段后、REVIEW阶段前，自动比对论文声明与清单中的预期值，生成编造报告。

### 4.3 独立评审Agent打破自确认偏差

**方案：** 自评审不应使用与研究Agent相同类型的Agent。修改`self_review.py`的`run_self_review()`，使其可以选择不同于研究Agent的评审Agent类型。或引入SciEval-Bench的多模型评审面板——使用GPT-4o、Claude、Gemini三个不同类型的LLM独立评分。

### 4.4 实验-论文一致性自动校验

**方案：** 在PAPER阶段完成后，自动运行校验脚本：从paper.tex提取所有数值型声明（使用正则匹配百分比、分数等）、从results.json加载对应度量值、比对偏差是否在容差范围内。超出容差的声明标记为"不一致"并注入评审反馈。

### 4.5 引用生成改为"检索→引用"而非"生成→验证"

**方案：** 改变PAPER阶段Agent的引用策略——不要求Agent"自主查找引用"（这容易编造），而是要求Agent"先检索后引用"——在撰写论文前，Agent需先通过Semantic Scholar API检索相关论文，将检索结果记录在`retrieved_refs.json`中，论文只能引用此文件中记录的论文。这从根本上杜绝了引用编造——Agent无法引用不存在于检索结果中的论文。
